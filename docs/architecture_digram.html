Crew Ops Advisor — Architecture

A deterministic rules engine computes every number, legality verdict, cost and ranking. A language model classifies intent, proposes entities, and narrates a result it never computed. A narration verifier checks the model's prose against the run's own fact ledger before a controller sees it.

Reflects the codebase as audited — including two fixes applied and gaps found open. See §5 for what's honestly unresolved.

4Multi-hop reasoning — where one answer needs several tool calls

A compiled plan is a fixed sequence declared in plans.py — every step's arguments come from entities already resolved from the question text. The rows below need a step's output to decide the next step's input, or an indirect id lookup the resolver doesn't chain today.

Query shapeWhat has to happen, in orderStatus today
"Who's flying DX412 tomorrow, and are they current on certs?" get_flight → read its crew list → feed each crew_id into get_certifications gap — get_flight already returns crew; entities.py::_infer_missing never backfills crew_id from a resolved flight_id. ~10-line fix, no new tool.
"Which reserve captain at BLR has flown the most hours this week — can they legally cover P-2291?" rank/sort reserves by duty hours (no tool does this) → take top-1 → check_legality on that id gap — needs a ranking tool (§6) before the id even exists to resolve.
"If C-3310 turns out to be unreachable, who's the next legal option — and is that option's own duty affected?" enumerate_cover_candidates → drop top result → re-run check_legality on candidate #2 with the new exclusion partial — the ranked list already contains #2; a true re-plan with a live exclusion needs a second classify→execute pass the graph doesn't do (one classify, one plan, no loop).
"How much of this week's reserve budget have we already spent, and does today's assignment push us over?" enumerate_cover_candidates → list_decisions (sum cost_inr) → compare against a budget gap — no aggregation tool over the decisions table; the data exists, nothing sums it.
"The captain on VT-DXA's pairing — what's their disruption risk, and who'd cover if it materialised?" tail+date → pairing_for (exists in _infer_missing) → role → crew_id → get_risk_signal → enumerate_cover_candidates works — this exact chain is already covered by _infer_missing's tail+date→pairing and pairing+role→crew rules. Good one to actually demo.

The architectural reason most of these are gaps: node_classify runs exactly once per question. There is no ReAct-style loop where a tool's result triggers another classification — by design, for latency and auditability (see README "Compiled plans over free-form tool calling") — but it means any question that needs that loop is currently answered by abstaining, not by attempting it badly. Consistent with "correctness outweighs coverage," but worth knowing which coverage that principle is costing you.

5Honest status — chaining, confidence, coverage, explainability

CapabilityStatusEvidence
Simultaneous disruptions
same instant, competing for one pool		 works solve_joint_assignment / MULTI_SICK is a genuine N-ary exhaustive solver (greedy fallback above 250k combinations) — not hardcoded to two openings. Verified with 3 simultaneous sick calls.
Chained disruptions
sequential, one changes the world for the next		 gap World.apply() only ever appends to lineage and, for crew-unavailability, unions into unavailable_crew. A 6h delay that breaches FDP-01 leaves the forked world's flight times byte-identical to the original — a chained cover/legality check afterward sees the undelayed schedule. Proven: DX412 delayed 6h → day-2 report is only 6.5h after the shifted release (needs 12h) and nothing surfaces it.
Confidence / uncertainty signalling computed, not shown Intent.confidence is computed (router score, LLM override margin) and recorded on every run, but the only place it's rendered is inside the collapsed "Show reasoning" panel on Advisor.tsx — off by default. Nothing on the answer surface itself signals low confidence.
Correctness > coverage genuinely embodied Three abstention guards (unresolved entity, compound-event regex, policy-question regex) are asserted in both directions by test_routing_and_honesty.py — they fire on bad shapes and all 38 graded questions still route to an answer. The cost: aggregate/ranking-style questions outside the 28 compiled intents abstain unconditionally, because no free-form planning fallback exists despite three separate docstrings claiming one does.
Explainability strong Every rule verdict carries an ArithmeticStep trace rendered by RuleProof; every rejection has a reason and a rule id (ExcludedTable); the fact ledger is exhaustive (1,887 facts on one Tier-3 answer, verified live). The one weak spot: the narration verifier grounds tokens independently, not claims — a fabricated causal pairing between two real facts (wrong crew ↔ wrong rule) passes verification today. Proven with a live repro.

6Tier 1 / Tier 2 — closing the credibility gaps

Retrieval (Tier 1)
  • rank_crew(criteria, top_n) — search_crew only filters; nothing sorts/ranks ("most senior", "least reachable") and returns a top-N.
  • Wire get_flight's existing crew list into entities.py::_infer_missing — the data is already there.
  • aggregate_query(metric, group_by, date_range) — sums/counts across flights or crew ("total block hours this week") have no home today; they abstain.
  • Surface existing roster inconsistencies (flagged_exceptions) as a live, queryable "what's already wrong today" lookup, not just a scenario fixture.
Legality (Tier 2)
  • check_legality_hypothetical(crew_id, report_utc, release_utc, sectors, aircraft_type) — today every legality check needs a real, existing pairing; forward roster planning can't ask "what if" without one.
  • project_duty_runway(crew_id) — "how many more duty days before C-1042 breaches DUTY-02/FLT-03 under a normal roster" doesn't exist; only current headroom does.
  • Expose flt03.STRICT as a strict_flt03 parameter on check_legality / simulate_duty_window — right now the 100h/28d hard-gate toggle is a code-level constant a controller can never actually flip.
  • A standalone reachability check (is_reachable(crew_id, required_report_utc)) — today this logic only exists buried inside candidate enumeration, unexplainable on its own.
